### 1. ОДНОЗНАЧНОЕ ОПРЕДЕЛЕНИЕ ЦЕЛЕЙ И КОНТЕКСТА

**Контекст среды:** 
Мы проектируем архитектурный и законодательный фундамент (Master `README.md`) для GitHub-репозитория, который будет управляться, наполняться и поддерживаться автономным AI-агентом (Arena AI Coding Agent или аналогичным). Конечным продуктом данного репозитория является комплексная инфраструктура развертывания (от 3-секционного USB-накопителя до глубоко иммунизированной ОС Windows 11 Enterprise LTSC IoT 24H2) для высоконагруженной DevOps-станции (ASUS Vivobook, i7, 16GB, 480GB NVMe). 

**Цель задачи:** 
Создание не просто описательного документа, а **машиночитаемого системного промпта (System-Prompt-as-a-Readme)**. Этот файл должен стать абсолютным контроллером (Control Plane) для AI-агента. Он должен принудительно ограничивать свободу агента математически строгими рамками (Negative Constraints), регламентировать уровни его автономности (Immutability Ranks) и задавать алгоритм взаимодействия с оператором (Human-in-the-Loop) на основе эмпирически доказанных тестов.

### 2. МОЕ ПОНИМАНИЕ ЦЕЛЕЙ (АРХИТЕКТУРНАЯ ИНТЕРПРЕТАЦИЯ)

Я понимаю поставленную задачу следующим образом: мне необходимо разработать **компилятор поведения для ИИ-агента**. 

Итоговый `README.md` будет программировать логику агента через следующие внедренные концепты:

1.  **Парадигма Полигона (Variable Path, Immutable Core):** Агент поймет, что он имеет право менять код, скрипты и подходы к решению задачи, но он **не имеет права** менять конечный ожидаемый результат (например, стабильную работу WSL2 без деградации SSD).
2.  **Ранги Иммутабельности (Immutability Ranks - IR):** Я введу строгую систему грейдов для всех директив и файлов:
    *   *IR-0 (High Autonomy):* Оптимизация PowerShell/CMD/Bash, добавление `Try-Catch`, рефакторинг Big-O сложности, логирование. (Агент делает сам).
    *   *IR-1 (Structural Autonomy):* Добавление вспомогательных функций внутри разрешенного стека. (Агент делает сам + пишет тесты).
    *   *IR-2 (Restricted Area):* Изменение хронологии фаз развертывания, модификация структуры USB-флешки, обход NTFS-изоляции. (Агент **обязан** провести масштабные A/B тесты, собрать метрики и запросить разрешение пользователя с доказательной базой).
    *   *IR-3 (Absolute Immutable):* Глобальные цели, отказ от WHP API, переход на запрещенный софт (VirtualBox/GUI-твикеры), изменение самого Master README. (Требует наивысшего уровня доказательств, анализа рисков и ручного аппрува).
3.  **Локальные шлюзы контроля (Local Gating Nodes):** Каждая вложенная папка репозитория будет содержать свой мини-`README.md`. Агент будет проинструктирован воспринимать эти файлы как локальные контекстные барьеры, запрещающие ему «выпадать» из контекста конкретной фазы при генерации кода.
4.  **Анти-Галлюцинаторный протокол (Anti-Generic Enforcement):** Прямой запрет на использование поверхностных, общеизвестных Windows-скриптов (типа `sfc /scannow` или банального отключения служб через `sc config`). Принуждение агента использовать наши верифицированные паттерны (WMI-Spoofing, SDDL-Удушение, C#-Декораторы).

### 1.1. Глобальная цель
Полный цикл создания монолитной, предсказуемой, долговечной рабочей станции ИТ-специалиста (частный сисадмин/DevOps) с нулевой толерантностью к фоновому «шуму», минимизацией износа (WAF) SSD и развертыванием бесконфликтной кроссплатформенной среды. Цикл алгоритмически включает в себя проектирование и реализацию 3-секционного загрузочного USB-накопителя, а также предварительную оптимизированную разметку и 4K-выравнивание целевого NVMe-накопителя (до установки ОС).

### 1.2. Аппаратная платформа (Целевая инфраструктура)
- **Устройство:** ASUS Vivobook
- **CPU:** Intel Core i7 (6P+8E ядер)
- **RAM:** 16GB
- **Storage:** 480GB NVMe SSD (Требует строгой GPT-разметки и выравнивания секторов)

### 1.3. Программная среда и Инфраструктура развертывания
- **ОС Хоста:** Windows 11 Enterprise LTSC IoT 24H2 (Сборка 26100.x).
- **Среда Pre-Execution (Live-USB):** WinPE11_10_8_Sergei_Strelec_x86_x64_2026.02.05_Russian.
- **Инструментарий Pre-OS Provisioning:** DiskGenius (бесплатная портативная версия из состава WinPE).
- **Внешний накопитель (USB 460GB):**
  - Раздел 1: FAT32 (Автогенерация Ventoy).
  - Раздел 2: exFAT (Кластер 512KB, 250GB) — Изображения, ISO, Бэкапы.
  - Раздел 3: NTFS (Кластер 16KB, Оставшееся место) — Скрипты, Инструменты, Драйверы.
- **Сетевой режим развертывания:** Изолированный (Карантинный).

### 1.4. Неизменяемые критерии успеха
- Абсолютное сохранение стабильности ядра ОС и отсутствие каскадной деградации.
- Физическое 4K-выравнивание (4K Alignment) всех логических разделов NVMe накопителя до начала копирования файлов ОС.
- Использование NTFS для рабочего раздела (исключение exFAT для поддержки POSIX/симлинков).
- 100% функциональность VMware (строго через WHP API) и WSL2/Docker одновременно.
- Использование строго бесплатного, портативного инструментария.

### 4.1. Gating Rules (Триггеры остановки для Arena AI)

### 🔬 ЭТАП 1: ИССЛЕДОВАНИЕ, АНАЛИЗ И СИСТЕМАТИЗАЦИЯ

**Симуляция 40 поисковых запросов выполнена.** (Векторы: Синтаксис GitHub YAML Issue Forms, спецификации автономных SWE-агентов, механизмы `.gitattributes` для PowerShell/Windows, приоритеты системных промптов `.cursorrules`/`.agentrules`, стандарты Markdown Any Decision Record - MADR).

**Выделенные паттерны и методологии:**
1. **Hardware Environment Forcing (Аппаратное принуждение):** ИИ-агенты часто игнорируют текстовые запреты в больших файлах. Но они не могут обойти настройки среды. Паттерн заключается в переносе правил из текста (`README.md`) в конфигурацию Git (`.gitattributes`) и GitHub (`.github/`).
2. **Schema-Driven Input (Схемный ввод):** Использование строгого YAML-формата для Issues, где агент не может написать вольный текст, а обязан выбрать один из вариантов (Dropdown) `GATE_TRIGGER`, заданных нами.
3. **Chain-of-Thought Guardrails (Ограждения хода мыслей):** Внедрение ADR-шаблона заставляет агента перед написанием кода формализовать свои намерения. Это включает у агента внутренний механизм рефлексии (Self-Correction).

**Детализированная система критериев успеха:**
1. Файл `gate_trigger.yml` должен иметь 100% валидный синтаксис GitHub Issue Forms (использование массивов `options` для `dropdown`, обязательных полей `validations: required: true`).
2. В файле `gate_trigger.yml` идентификаторы шлюзов должны побайтово совпадать с Section 4.1 из `README.md`.
3. Файл `.gitattributes` должен жестко форсировать CRLF (Carriage Return Line Feed) для скриптов `.ps1` и `.bat`, так как Linux-окружение Arena AI Agent по умолчанию генерирует LF, что ломает исполнение в WinPE/Windows.
4. Файл `.agentrules` должен быть лаконичным, без "воды", содержать жесткие императивы (MUST, DO NOT) и прямую ссылку на `README.md`.

### 2. СИСТЕМАТИЗАЦИЯ ИССЛЕДОВАНИЙ (ПАТТЕРНЫ ВЗАИМОДЕЙСТВИЯ)

Симуляция 40 запросов показала, что автономные SWE-агенты (Software Engineering Agents) страдают от трех главных проблем:
1. **Context Blindness (Слепота контекста):** Если при первой задаче не заставить агента принудительно прочитать весь `README.md`, он начнет фантазировать (галлюцинировать) архитектуру.
2. **Action Overload (Перегрузка действиями):** Если дать команду «Реализуй Фазу 1», агент попытается за один коммит написать 10 скриптов, игнорируя создание ADR (документации). Задачи нужно дробить на микро-транзакции.
3. **Conversational Drift (Смещение в диалог):** Общение с агентом как с чат-ботом («Привет, а давай немного переделаем этот кусок...») разрушает его системный промпт. Общение должно быть транзакционным, как командная строка (CLI).

**Суть:** Агент сформировал Pull Request (PR). Он заполнил наш шаблон с чек-боксами. Вы проверили код скрипта и увидели, что он использовал платную утилиту (нарушение Section 1) или забыл про CRLF.

> **ШАБЛОН ПРОМПТА 4: Корректировка кода (Review-Prompt)**

> *Аннотация:* Агент воспринимает такой формат как вызов компилятора. Он не будет спорить, он перейдет в ветку, исправит указанную строку и обновит Pull Request.

### 1. АНАЛИЗ И ОДНОЗНАЧНОЕ ОПРЕДЕЛЕНИЕ (ОТВЕТЫ НА ВОПРОСЫ)

Я критически проанализировал ваши вопросы. Они бьют точно в цель и выявляют логические зазоры в текущей архитектуре графа зависимостей (Semantic Graph). Ниже приведено мое понимание и инженерное обоснование по каждому пункту:

**Вопрос 1: Ссылка на паттерн в `PULL_REQUEST_TEMPLATE.md`**
*   **Мой анализ:** Вы абсолютно правы. Требовать от ИИ указать тег `[PAT-XXX]`, но не требовать физическую ссылку на файл паттерна — это нарушение логики графа. Если паттерн применен, ИИ должен явно указать путь к его спецификации.
*   **Решение:** В PR-шаблон будет добавлена строка: `- Использует паттерн: [PAT-XXX] (ссылка на docs/patterns/PAT-XXX.md)`.

**Вопрос 2: Создание шаблона `0000-PAT-TEMPLATE.md`**
*   **Мой анализ:** Это критически важное упущение. Если ИИ-агент в ходе Web-Search найдет новый эффективный способ (например, обход нового реаниматора в LCU 24H2), он должен сначала формализовать этот метод как "Паттерн", чтобы его можно было переиспользовать (DRY) в других скриптах. Без шаблона ИИ напишет спецификацию хаотично.
*   **Решение:** Будет разработан файл `docs/templates/0000-PAT-TEMPLATE.md`. Он будет включать: Суть паттерна, Вектор применения (на что воздействует), Код/Механику паттерна и Ограничения.

**Вопрос 3: Перенос паттернов из `README.md` в папку `docs/patterns/`**
*   **Мой анализ:** Держать *содержимое* паттернов в README.md — это раздувание (Bloat) монолита. README должен оставаться легким навигационным манифестом.
*   **Решение:** В `README.md` (Section 3) останется только **Таблица-Реестр** (Индекс: ID + Имя). А физически каждый паттерн (`PAT-01.md`, `PAT-11.md` и т.д.) будет лежать как отдельный файл в `docs/patterns/`. Это дает каждому паттерну "физическое" место в топологии.

**Вопрос 4: Перенос папки `docs/` внутрь `builds/devops_ltscIot24h2/`**
*   **Мой анализ (Архитектурная вилка):** Здесь возникает конфликт парадигм *Bounded Context (Полная инкапсуляция)* и *DRY-Fidelity (Переиспользуемость)*. 
    *   Если мы перенесем `docs/` внутрь `builds/devops_ltscIot24h2/`, мы добьемся идеальной изоляции. Репозиторий превратится в папку, где лежит только 1 проект, и всё его содержимое внутри.
    *   **НО:** Паттерны (например, `PAT-11 NTFS Deny SYSTEM` или `PAT-12 Disable VBS`) являются универсальными (OS-level). Если в будущем вы захотите создать в этом же репозитории сборку `builds/office_ltscIot24h2/` или `builds/gamedev_ltscIot24h2/`, перенос `docs/` внутрь конкретной сборки заставит нас дублировать файлы паттернов и шаблонов (`0000-STAGE-TEMPLATE.md`) для каждой новой сборки. Это прямое нарушение аксиомы `ZERO-Redundancy`.
*   **Мое архитектурное предложение:** 
    Папка `docs/templates/` (Правила игры репозитория) и `docs/patterns/` (База знаний механизмов ОС) должны остаться в **корне** репозитория как глобальная (Global Immutable) библиотека.

- `[IR-3] Workspaces`: Пространство конкретной сборки (`builds/devops_ltscIot24h2/`). Полностью мутируемо.

### 2.2 Сущности проекта и CRUD-Протоколы
Разработки и исследования внутри репозитория ведутся строго через семантический граф зависимостей: `[STG-XXX]` → `[ADR-XXX]` → `[PAT-XXX_date_name]` → `[SC-XXX]`.

1. **[SC-XXX] (Success Criteria):** 
   - **Определение:** Константы проекта (Section 1.3). 
   - **CRUD:** Только Чтение (R).
2. **[PAT-XXX_date_name] (Pattern):** 
   - **Определение:** Изолированный ИТ-механизм (например, `PAT-011_2024-10-25_ntfs_deny_system_lockdown.md`). Хранится в `docs/patterns/`. 
   - **CRUD:** Чтение (R). Обновление (U) даты и содержимого при устаревании. Создание (C) нового файла по шаблону `0000-PAT-TEMPLATE.md` при нахождении уникального механизма.
3. **[ADR-XXX] (Architecture Decision Record):** 
   - **Определение:** Документ, обосновывающий применение `[PAT]` для `[SC]` в конкретной сборке. Хранится в `builds/devops_ltscIot24h2/docs/decisions/`. 
   - **CRUD:** Создание (C) при проектировании новых скриптов. Чтение (R).
4. **[STG-XXX] (Stage):** 
   - **Определение:** Хронологический шаг конвейера. Обязан ссылаться на `[ADR]`. Хранится в `builds/devops_ltscIot24h2/algorithm/`. 
   - **CRUD:** Создание (C), Обновление (U), Чтение (R).
5. **[STUB] (Shadow Stub):** 
   - **Определение:** Markdown-паспорт бинарного файла (`.md`).
   - **CRUD:** Создание (C) и Обновление (U) строго по шаблону `0000-STUB-TEMPLATE.md`. Коммит реальных бинарников ЗАПРЕЩЕН.

### 2.3 RAG Pipeline: 4-Стадийное Исследование (ОБЯЗАТЕЛЬНО)
Перед генерацией кода (скриптов/алгоритмов) агент ОБЯЗАН выполнить конвейер:
1. **Filtering:** Сканирование `docs/patterns/` и выделение списка PAT-файлов, релевантных текущей задаче.
2. **Validation (Web-Search):** Обязательный поиск актуальных ИТ-спецификаций во внешней сети (интернет) с целью верификации собранных паттернов.
3. **Updating (U):** Если Web-Search выявил конфликты (устаревшие ключи реестра, измененные CLI-аргументы DISM/Sysprep), агент исправляет PAT-файл и обновляет дату в его `snake_case` имени.
4. **Crystallization (C):** Если Web-Search выявил новый перспективный механизм, не имеющий двойника в `docs/patterns/`, агент создает новый PAT-файл по шаблону. 
*Только после этого шага ИИ приступает к написанию ADR и кода.*

## SECTION 3: GATING RULES (ШЛЮЗЫ АВТОРИЗАЦИИ) [IR-0]
При нарушении правил или конфликте зависимостей агент прерывает работу и создает Issue (шаблон `gate_trigger.yml`):
- **GATE_IMMUTABLE:** Попытка U/D операций в зонах `[IR-0]`.
- **GATE_AMBIGUITY:** Нехватка контекста, провал Web-Search или A/B тестов.
- **GATE_TOOL_REPLACE:** Предложение внедрения непортативного/платного ПО.
- **GATE_STRUCTURE:** Нарушение топологии `[IR-1]` или создание файлов вне Workspaces.
